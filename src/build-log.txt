SESSION 1 / PHASE 1 (2026-10-02, Opus): THE DETERMINISTIC CORE IN ENGINE:WORLD. COMPLETE.
  ENGINE:WORLD: var ENGINE_WORLD, deep frozen, version 1.0.0, one global, reads no host global. The render engine is passed
    in as an argument wherever it is needed (climate.table(art, render)), so Day 150 loads engine-world.js beside
    engine-render.js unchanged. Later phases add src/engine-<part>.js sections spliced above the freeze line by build.js
    (engine-progression, engine-overworld, engine-interiors, engine-zones, engine-checks, in that order when present).
  Determinism rules (static scan in phase1): no Math.random; no for in; Object.keys only inside util.keys, which sorts;
    no Date or performance; DECISION: no transcendental Math (sin, cos, tan, exp, log, pow, atan, hypot, cbrt and kin),
    because their last bits may differ between browsers and a world must regenerate identically on any device when it is
    not baked. sqrt, floor, abs, imul, and the four basic operations are exact under IEEE 754.
  API: util {keys, each, clamp, digest (FNV-1a over numbers rounded to 1e-9 or strings)}; hash {xmur3, str (first output),
    seed(master, key) = str(master + '|' + key)}; mulberry32; rng(seed) -> fn with int, range (inclusive), float, chance,
    pick, shuffle (Fisher-Yates on a copy), weighted (weights or {w}; index or -1); ids {PREFIXES, slug,
    structural(prefix, key) = prefix + slug(key, 40) + '_' + 4 base36 chars of str(prefix + key), always valid for
    ID_RE, refuses non world prefixes}; noise {simplex(seed) -> {noise2} (Gustavson 2D, permutation shuffled by
    rng(seed), 12 gradients, output in [-1, 1]), fbm(gen, x, y, o), ridge(gen, x, y, o) (octaves of (1 - |n|)^2, in
    [0, 1]), field(w, h, seed, o) -> Float64Array, o {octaves 4, lacunarity 2, gain 0.5, frequency 1, scale 32, ridge}};
    each octave is offset (k * 19.19, k * -7.31) so octaves never line up at the origin; quantize {band(v, th) = number
    of the four cut points v reaches, bands, quantile(arr, fractions) cut points by sorted rank, normalize to [0, 1]};
    climate {index(t, m, e) = t*25 + m*5 + e, inBox, table(art, render), lookup(table, t, m, e)}.
  Climate table: calls render.tiles.matchClimate(tils, t, m, e) for all 125 cells over the biome tilesets in
    render.tiles.prioList(art) order, recording each cell's tileset ID and whether the point lies inside that box.
    Returns {order, cells, exact, exactCount, nearestCount, features [{id, key, feature, temp, moist, elev}], keys, digest}.
    Default biomes: 109 exact, 16 nearest (coast at temperature 0 elevation 1; swamp, forest, grassland at a few wet or hot
    corners). Feature biomes (volcanic) never fill a cell; they are listed for Phase 3's placement pass. Editing a box in
    the art changes the table, and a deleted biome falls back to the nearest box, never to nothing.
  FINDING for Phase 3: at temperature 0 the table gives Snowfield, not Mountains, for elevation 4 (the snow box is tighter
    and wins), and Snowfield is passable (flags 3). Walls, region ridges, and landing beach rings must therefore be placed
    with the mountain biome directly (the tileset whose box is elevation 4 and flags 0), not looked up through the table,
    or a cold ridge would leak. Elevation 0 is Ocean in every column.
  Speed: a 256 by 256 five octave field takes about 150 ms in Node here; the climate table about 2 ms. Phase 3 runs several
    layers, so the Web Worker (importScripts engine-world.js) is likely needed on mobile; measure in Phase 3 before adding.
  Tests: test/phase1.js 37 of 37 (static scan; identical digests for six seeds in two vm contexts and in the page; every
    probe differs between seeds; sub seeds; uniformity of mulberry32; range, shuffle, weighted 5 5 5 1; simplex range,
    mean, continuity; fbm and ridge ranges; octave, lacunarity, gain sensitivity; band, quantile, normalize; sorted
    iteration; 1500 arbitrary keys give valid IDs, prefix and key only, no collisions in the four continent fixture; the
    climate table against matchClimate cell by cell, in two contexts and the page, 109 exact, volcanic as feature, the
    snowfield finding, box edits, deleted biome; timing). test/phase0.js still 63 of 63.
  Next: Phase 2, the progression graph before geometry (src/engine-progression.js plus the WORLD side that turns the graph

SESSION 2 / PHASE 2 (2026-10-02, Opus): THE PROGRESSION GRAPH BEFORE GEOMETRY. COMPLETE.
  Session start: the repo built clean and phase0 63/63, phase1 37/37 before any change.
  ENGINE:WORLD section src/engine-progression.js (spliced above the freeze line): ENGINE_WORLD.progression {DEFAULTS,
    settings(s), build(spec, settings), walk(graph), check(graph), gate {chapter(id), seal(id), SHIP, AIRSHIP}}. Pure data
    in, plain data out: the engine reads plain specs, never the bundle. DECISION: the graph uses no randomness and never
    reads the seed, so a reroll moves terrain, never the story's order, and every graph regenerates identically anywhere.
  Spec (WORLD.progression.spec): chapters in Charter order as {chapter, name, continent slug, label, minutes, bosses}, with
    bosses = sorted trp_ IDs that have an isBoss member and that chapter.
  Gate keys (world local, Day 149 binds them): chapter:<chp>, item:seal:<chp>, vehicle:ship, vehicle:airship. DECISION: the
    chapter local golden item is named item:seal:<chp ID>. Chapter 1's key is held at the start (graph.start).
  Golden path per chapter, in order: twn start (needs chapter key), dgn key (grants item:seal), gate lock (needs chapter key
    and seal), dgn boss (needs chapter key and seal; grants the next chapter's key and any vehicle), gate exit (needs the
    next chapter's key, plus the ship for a landing; via 'pass' or 'landing'; to the next region). The finale has no exit
    and its boss interior is 'castle'; other bosses and key dungeons are 'dungeon', caves 'cave', towns 'town' (Phase 4
    hints). Lock and exit are gates, not sites: they make no records; Phase 3 places them (the lock in front of the boss
    dungeon, the exit as the pass ridge or landing ring). DECISION: every site, golden or optional, needs its own chapter's
    key, so neither the airship nor an open pass can break sequence; Phase 6's flood fill must treat a site's entrance as
    closed until its chapter key is held (the airship reaches every land cell, not every site).
  Ship: with the boss of the chapter before the first chapter on a new continent (none when there is one continent).
    Airship: with the boss of chapter round(airshipAt x N), clamped to 1..N-1, only when later than the ship; airshipAt 0
    disables it. DECISION: 'landing' means the continent differs from the previous chapter's, even when it returns to an
    earlier continent, and every landing needs the ship (always held by then). Region entry is start, pass, or landing.
  Optional branches after the golden path: cavesPerChapter caves (dgn role cave, or cave1..caveN when more than one), plus
    twn role town in chapter one when secondTownInChapterOne. They grant nothing.
  Bosses: the boss node takes the first sorted boss troop; others ride in spareBosses for Phase 5. A chapter with none gets
    one graph warning (code no-boss) and troop null.
  walk: a topological walk from graph.start, one node at a time in graph order, collecting grants; returns order, held,
    stuck, grantedAt, openedAt. check: unreachable, never-granted, key-after-lock, optional-golden, key-chapter (chapter n's
    key granted anywhere but chapter n - 1), seal-chapter, ungated.
  Structural keys use chapter IDs, not indexes (twn|<chp>|start, dgn|<chp>|key, dgn|<chp>|boss, dgn|<chp>|cave,
    twn|<chp>|town, reg|<chp>), so inserting or reordering chapters never renames a site Day 149 may reference.
  WORLD side, new fence src/world-generate.js (WORLD:GENERATE): WORLD.progression {spec, preview, graph, stale, apply}.
    apply builds, refuses an unsolvable graph, writes one reg_ per chapter {chapter, continent, continentLabel, part (1, 2..
    within a shared continent), entry, order, sites [ids], next (reg_ id or null), exitGate {gate, kind, requires}} and a
    twn_ or dgn_ per site {chapter, continent, region (reg_ id), role, golden, optional, interior, requires, grants, order;
    boss adds troop, spareBosses, finale}. world.progression holds the whole graph; each site node gains record (its ID),
    each gate node regionRecord. A record with origin 'user' is never overwritten; a generated reg_, twn_, or dgn_ the
    graph no longer has is removed. map_ and npc_ are not touched. Counts: demo 2 reg_, 3 twn_, 6 dgn_; four 6, 7, 18.
  Validator world.graph (runs once a graph exists): check() problems as errors, no-boss as warnings, a stale graph (Charter
    or settings changed since layout, by digest) as a warning, and a site record missing from the records as an error.
  UI: Start gains a Progression card above the climate table: Lay out progression (or Lay out again), a solvable chip with
    the walk length, ship and airship chips, a stale chip, and one row per region (entry and optional sites under the name,

DECISIONS (2026-10-02, from the Planning session, accepted as the plan of record):
  World follows Day 147's open policy; filling sdq_.giver is the only write outside world. Day 148 mints no flg_; gates use
  world local keys (chapter:<chp id>, vehicle:ship, vehicle:airship, item:<key>) that Day 149 binds later. The climate
  lookup caches matchClimate in prioList order. Caves and castles use interior:dungeon unless the bundle has
  interior:cave or interior:castle. Towns carry no zone table and building floors are flag 1. Boss troops are found by

  map's sub seed is hash.seed(master, key). Generators ship as engine-world.js. Default overworld 96 plus 32 per
  continent, capped at 256 square.
